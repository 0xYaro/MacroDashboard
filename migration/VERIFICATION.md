### The one recorded denominator this migration does not match

**2026-W36 S2.** the 2026-W37 journal recorded n = 6 for W36's S2 while recording n = 9 for W36's S1 on the opposite convention; the parse keeps all 8 stated target legs.

This is a discrepancy in the source, not a parse error, and the parse is deliberately not changed to match it.

Both counts were written by the same grading block in the 2026-W37 journal, on opposite conventions.
It counted 2026-W36's S1 as **9**, which only reaches 9 by counting its three non-numeric legs (`Nasdaq leads`, `Russell lags`, `SOL leads`), and the journal's own prose enumerates all nine.
It counted 2026-W36's S2 as **6**, which only reaches 6 by excluding its two equivalent non-numeric legs (`ETH catches up`, `curve steepens`) from the eight the scenario states.
The two counts cannot both be right.

This is the clearest evidence in the whole migration that `macro_core.scenario_target.kind` had to exist.
A leg like `curve steepens` is a stated forecast and belongs in the denominator, but it is not a band and can never be auto-scored, so counting it and machine-checking it are two different questions.
Before `kind`, a grader had to answer both with one number and answered them inconsistently inside a single block.
With `kind`, W36's S2 is 8 targets of which 6 are bands and 2 are manual, which is exactly the pair of numbers the journal was trying to express.

The parse keeps all 8 stated legs, because dropping one would make the scenario look more checkable than it was.
2026-W36's S2 was not that week's base case, so the Scorecard Ledger's `6 of 9` for 2026-W36 is unaffected and `week_grade` is correct.

## Contract and schema issues

`docs/CONTRACT.md` is binding and this migration does not edit it.
Every disagreement found between the contract, `supabase/migrations/*.sql` and what the sources actually contain is listed here.

### macro_core.setup NOT NULL against the null-never-zero doctrine

entry_lo, entry_hi, invalidation, invalidation_dir and target are NOT NULL.
The Setup Ledger contains one setup whose entry is a condition rather than a band and three whose invalidation names a level with no side, so those fields have to be derived to load at all.
Each derivation is named in this report, and the rule that derives a side is checked against every row where the journal did write one.

### macro_core.setup_grade.graded_week NOT NULL leaves an ungraded setup nowhere to sit

The Setup Ledger's four 2026-W39 rows read `open (grade in W40)`, which is a placeholder rather than a grading.
Writing 2026-W40 into graded_week would assert a grading that has not happened, so those four setups carry no setup_grade row and the 2026-W40 Monday run writes the first one.
If the app needs an ungraded setup to be visible as `open`, that belongs in macro_mart.setup_state, which already has an entry_state of `not triggered`.

### No journal records whether an individual trigger clause fired

macro_core.condition_state_asserted now holds the status a manual condition was written with, and a phase tracker row supplies one directly.
A trigger clause does not: the grading journals judge a trigger as a whole: `the trigger fired in full`, `not one trigger clause fired`.
Every migrated clause is therefore asserted `unevaluable` and carries that whole-trigger verdict as its current_text, rather than having a per-clause verdict invented for it.

### CONTRACT.md's cadence vocabulary does not include `continuous`

The 'Sources and their cadence' summary table calls BTC, ETH and SOL continuous, which is not one of the five values the same document defines for macro_core.series.cadence.
config/series.yaml has already resolved this as daily on a calendar_day release rule; the summary table still says continuous.

### The 2026-W37 journal records two different target-counting conventions

It counts 2026-W36's S1 as 9 including three non-numeric legs and, in the same block, counts W36's S2 as 6 excluding two equivalent ones.
This is a source defect rather than a contract issue, but it is the one recorded denominator this migration does not reproduce, so it is listed here too.
